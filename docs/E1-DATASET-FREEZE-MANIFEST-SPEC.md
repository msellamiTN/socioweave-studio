# E1 benchmark freeze manifest specification

**Status:** implementation contract; no benchmark snapshot currently approved  
**Source:** uploaded paper, Section 8.1, Tables 12–14  
**Scope:** provenance, sampling traceability, dataset-native reference preservation and immutable snapshot identity.

## 1. Paper requirements versus implementation choices

The paper specifies:
- four public benchmarks plus a fifth study-specific smart-administration set (Section 8.1);
- 100 prompts from each public benchmark and 60 smart-administration prompts (Section 8.1; Table 13);
- dataset-specific references and metric applicability (Table 12);
- prompt tags for number of constraints, ambiguity, coupling of the reference decomposition and conflicting objectives (Section 8.1);
- five seeds per configuration (Table 13).

The paper does **not** specify the public prompt IDs, public dataset split names, sample-selection algorithm, selection seed, TaskBench domain allocation, BREAK configuration choice, immutable release revisions, or license approval procedure. Those are protocol decisions. They must be explicitly declared before running the experiment and reported as operational choices, not attributed to the paper.

The five experimental seeds in Table 13 are run-level seeds. They are not a dataset sampling seed. A dataset selection seed is a separate optional field and must not be conflated with the five run seeds.

## 2. Frozen per-dataset declaration

The E1DatasetSource declaration now requires:

| Field | Purpose |
|---|---|
| path | Exact operator-supplied local JSONL snapshot |
| source_url | Canonical upstream source or documented author-release location |
| source_revision | Immutable commit, release tag plus resolved commit, archive version, or equivalent stable identifier |
| source_version | Human-readable dataset release/version |
| split | Exact native split represented by every row in the file |
| eligible_population_count | Number of eligible examples in the declared source population before selection |
| selection_protocol | Reproducible description of filtering, stratification and selection |
| selection_seed | Optional non-negative seed if selection is randomized; omit only for a fully enumerated deterministic ID list |
| license_url | Dataset-specific license/terms or documented author-provided rights record |
| license_identifier | Exact license identifier or explicit rights status; never infer from the code repository |
| license_review_status | Must be approved before freezing |
| license_review_evidence | Review record, decision reference, attribution analysis and any upstream component-source assessment |
| license_reviewed_by | Accountable reviewer identity/role |
| license_reviewed_at | Timezone-aware ISO-8601 review timestamp |

A repository's code license is not automatically the license for its datasets. For aggregated datasets, upstream component data terms must be assessed separately. The approved value is an operator attestation backed by recorded evidence; software validation cannot itself grant legal permission.

## 3. Row-level JSONL contract

Each selected row contains:
- example_id: stable native identifier (or a documented stable ID derived from source-native keys);
- prompt_text: exact user request text used in the experiment;
- split: exact native split;
- metadata: scalar tags and provenance such as domain, source-native ID, constraint/ambiguity/coupling labels and source configuration;
- reference_data: structured dataset-native reference material required by Table 12.

Reference mapping must preserve the semantics and native fields. Do not flatten a graph into an unordered string, omit evidence, or manufacture a gold decomposition where Table 12 says none exists.

| Dataset | Minimum reference content to preserve |
|---|---|
| BREAK | Gold decomposition and ordered steps |
| StrategyQA | Annotated decomposition, evidence and answer |
| TaskBench | Reference sub-task graph, nodes and dependencies |
| TravelPlanner | Annotated constraints and final-plan checks/reference information; **not** a reference decomposition |
| smart-administration | Requirement lists, hypotheses and practitioner-reviewed reference decompositions |

The loader checks that reference_data is present and JSON-compatible, but semantic completeness still requires dataset-specific validation and human/source audit.

## 4. Snapshot manifest generated by the engine

The frozen manifest records, per dataset:
- canonical source URL, immutable upstream revision and source version;
- local source filename and SHA-256 of exact JSONL bytes;
- declared split and eligible population size;
- selection protocol, optional selection seed and exact selected IDs;
- license identifier/URL, approval status, reviewer, timestamp and evidence reference;
- prompt count and prompt/reference hashes for every selected ID;
- paper source, prompt case, reference description, metric applicability and coverage scope.

The top-level manifest records schema version, dataset order, total prompt count (460) and a content hash over the complete dataset entries. Any change to file bytes, selected IDs, prompts, references or provenance changes the snapshot hash.

## 5. Selection protocol requirements

A selection protocol must be sufficient for an independent researcher to recreate the selected ID list from the pinned eligible population. It must state:
1. source revision and exact split/configuration;
2. all eligibility filters and exclusions;
3. whether sampling is random, stratified, systematic or an explicitly curated list;
4. for stratification, each stratum and its target count;
5. the selection algorithm and seed when random;
6. deterministic tie-breaking and stable ID ordering;
7. the final selected IDs and count.

Do not select the first 100 rows merely because that is convenient. Do not use model outputs, decomposition quality, or evaluation scores to choose prompts. The prompt-feature tags required by Section 8.1 must be recorded with an explicit tagging procedure; the reference-based coupling tag must be computed from the reference decomposition where one exists, not guessed from the prompt.

## 7. Fail-closed acceptance gates

The snapshot may be considered frozen only if:
- exactly five datasets are present with counts 100, 100, 100, 100 and 60;
- each source file matches its declared split and has unique stable IDs;
- every source has an immutable revision and non-empty source URL;
- every selection protocol and eligible population count is declared;
- every selected ID is recorded and the count does not exceed the eligible population;
- every dataset has an approved license review with traceable evidence and timezone-aware reviewer timestamp;
- all Table 12 reference structures are present and pass dataset-specific semantic checks;
- prompt-feature tags and their annotation protocol are available;
- the manifest and source files are archived immutably and their hashes independently rechecked.

Passing software validation means only that the declared snapshot is structurally and cryptographically consistent. It does not certify the truth of source claims, legal permission, semantic reference correctness, or fidelity to an undocumented sample from the original study.
